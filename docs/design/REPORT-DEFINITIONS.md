# 报表口径定义（S4）

日期：2026-11-10 建，2026-11-12 更新（N3 统计 UI 落地）。实施人：Claude Code。

本文定义人事概览的统计口径与预期值，并记录已执行的核对证据。统计全部由后端 API
在角色数据范围内计算，不使用付费 BI。

## 1. 口径

| 指标 | 定义 | 计算方式 |
|---|---|---|
| 在职人数 | 任职状态为 `PROBATION` 或 `REGULAR` | `count(status in [PROBATION, REGULAR])` |
| 待转正人数 | 任职状态为 `PROBATION` | `count(status = PROBATION)` |
| 待审批数 | 转正申请状态为 `PENDING`（按授权范围） | `count(confirmation_requests.status = PENDING)` |
| 部门人数 | 按当前部门分组，只统计在职 | `group by department`，过滤 `PROBATION/REGULAR` |

> 明确区分：**待转正人数 ≠ 待审批申请数**。前者是“试用期员工数”（8），后者是“待
> 处理的转正申请数”（初始 0）。

## 2. 初始预期值（种子数据）

| 指标 | 预期 |
|---|---|
| 员工总数 | 20 |
| 在职人数 | 18（试用 8 + 在职 10） |
| 待转正人数 | 8 |
| 离职人数 | 2 |
| 部门人数（在职） | 技术部 7、产品部 7、市场部 4 |
| 待审批数 | 0 |

通过一条转正后：在职仍 18、试用变 7、待审批回 0（员工状态 PROBATION → REGULAR）。

## 3. 已执行核对（[verify_reports.py](../../scripts/verify_reports.py)）

结果：**通过 12 / 12**。关键断言：

- 初始在职 18、待转正 8、离职 2、部门 `{技术部:7, 产品部:7, 市场部:4}`。
- 主管 A 员工范围仅 8 人（非全公司 20），员工 A 仅 1 人 —— 统计不泄露越权数据。
- 提交后 HR 待审批 1；通过后在职仍 18、试用 7、待审批 0。

命令与断言详见 [VERIFICATION.md](../quality/VERIFICATION.md) 第 3 节。

## 4. UI 展示（N3 已交付，2026-11-12 浏览器实测）

「人事概览」页（仅 HR 菜单可见）用数据可视化插件（charts，社区版免费）的
**统计卡**与**表格**区块展示，计数由服务端 `charts:queryData` 在角色数据范围内
聚合（口径同上），不依赖 20 条分页结果：

- 四张统计卡：在职人数（18）/ 试用人数（6）/ 待审批数（1）/ 离职人数（2）；
- 部门在职人数表：技术部 7 / 产品部 7 / 市场部 4（按部门分组，只计在职）；
- 员工明细表：工号/姓名/部门/职位/任职状态。

实测证据（无头 Chrome + CDP，`docs/evidence/n3-*.png`、`n3-stats-console.txt`）：

- 卡片值与 HR token 直接调 `charts:queryData` 的全量口径逐一相等；
- 审批联动：主管在浏览器通过一条申请后，在职不变（18→18）、试用减一（7→6）、
  待审批减一（1→0）、明细同步（该员工“试用中”→“正式”）；
- 越权双层验证：员工/主管菜单无「人事概览」；用其 token 直接调 `charts:queryData`
  请求"全公司在职"计数，服务端仍按数据范围过滤（员工=1 本人，主管=7 本组），
  拿不到全公司 18。

页面构建见 [build_pages_v2.py](../../scripts/build_pages_v2.py)（`hr_overview_blocks()`），图表 schema 的
平台 quirks 见 [LIMITATIONS.md](../quality/LIMITATIONS.md) §3。主管与员工不能访问全公司聚合数据
（后端 ACL 强制，菜单只是第一层）。
